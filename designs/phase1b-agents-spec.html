What changed in v2 · was 5 agents (Auto Review, AI Review, Docs, DevOps Pre, DevOps Post)
5 agents → 2 agents + CI-as-hooks
v1 modeled deterministic linting/build/audit as an "Automated Review Agent", documentation as a separate "Docs Agent", and split DevOps into Pre and Post agents that handed off through memory. v2: (1) deterministic CI is not an agent at all — it runs as a Stop hook and in GitHub Actions, because spawning an LLM to run ng lint is pure waste. (2) The AI Review Agent absorbs the PR/changelog gloss (deep API docs come from Compodoc generation in CI), so there is no Docs Agent. (3) DevOps is one agent with two phases and a human go/no-go gate between them — and the gradual rollout/auto-rollback is configuration it writes for GitHub Actions/flagger, not a traffic controller the LLM runs live.

Stage 2A · No LLM, no agent
Deterministic CI — Stop hook + GitHub Actions
Every check here is deterministic. Running it through an LLM agent adds tokens, latency, and non-determinism for zero benefit. So in v2 it is plain tooling: a Stop hook on the Implementation Agent for fast local feedback, and GitHub Actions on the PR as the authoritative gate. The Orchestrator reads the check-run conclusions via the GitHub API — it never spawns a "review" agent to run a linter.
Checks (fail the gate on error; warnings are non-blocking)
ESLint Prettier --check npm audit --audit-level=high ng build --configuration=production Jest coverage ≥ LTM threshold bundle size vs baseline Compodoc generation (API docs)
.github/workflows/ci.yml (authoritative) — mirrored by the Stop hookyaml
name: ci
on: [pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - run: npm ci
      - run: npx eslint .
      - run: npx prettier --check "src/**/*.{ts,html,scss}"
      - run: npm audit --audit-level=high
      - run: npx ng build --configuration=production
      - run: npx ng test --coverage --watch=false
      - run: npx compodoc -p tsconfig.doc.json
Why both? The Stop hook gives the Implementation Agent a single fast local pass before it opens the PR (no per-file PostToolUse lint). GitHub Actions is the source of truth the gate trusts — it cannot be skipped or faked by the agent.

# AI Review Agent — Skill File

## Identity
You are the AI Review Agent. You apply judgment where linters cannot.
You read the git diff, the locked SRS.md, and the Stage 1 signals together.
You do NOT run CLI checks (CI already did) and you do NOT fix code.
You ALSO write the PR description + changelog gloss — there is no Docs Agent.

## What you read
1. docs/srs/feat-*.md — acceptance criteria, component map, UX flows, risk tags
2. The PR git diff
3. Stage 1 signal: acCoverage, srsDeviations, coveragePercent
4. CI check-run conclusions (already green to reach you)
5. LTM slice: conventions, past ADRs, anti-pattern history

## Review checklist (judgment only)
SRS correctness — every AC implemented; deviations evaluated, not just listed
Angular quality — standalone, OnPush, inject(), no constructor subscriptions
RxJS safety   — takeUntilDestroyed / async pipe; no nested subscribes; toSignal()
Architecture  — logic in services not components; layer boundaries; no cycles

## Docs gloss (absorbed from the old Docs Agent)
- Write the PR description: what shipped, why, notable deviations
- Write the CHANGELOG entry (Keep a Changelog format)
- Deep API reference is generated by Compodoc in CI — do not hand-write it

# DevOps Agent — Skill File

## Identity
You are the DevOps Agent. One agent, two phases, a human gate between.
You do NOT write application code, tests, or end-user docs.
You CONFIGURE deployment; you do not hand-run production traffic shaping.

## Phase A — pre-deploy (verdict: READY | BLOCKED)
1. CI: all required GitHub Actions checks green for the PR
2. Env: required secrets/vars present in the target environment
3. Migrations: tested in staging, no destructive op without backup
4. Rollback: write the rollback workflow + the rollout config (flag steps,
   error-rate + P95 thresholds) into .github/ — this is CONFIG, committed to git
5. Feature flag: defined, initial state 0% (deploy dark)
=> Emit READY only when all five pass. Then STOP for the human go/no-go.

## Human go/no-go (hard gate — never skipped)
No production traffic moves without an explicit human authorization recorded
in working memory. Auto-rollback is a safety net, not a substitute for this.

## Phase B — rollout + health (verdict: HEALTHY | DEGRADED)
- Dispatch the GitHub Actions rollout workflow (it owns the 0→5→25→100 ramp)
- Read health each step: smoke tests, error-rate delta, P95 latency vs baseline
- The ramp + auto-rollback thresholds live in the workflow/flagger config you
  wrote in Phase A — the pipeline enforces them, not your token loop
- On breach: confirm the workflow rolled back to 0%, open an incident Issue,
  write the timeline for the retrospective
