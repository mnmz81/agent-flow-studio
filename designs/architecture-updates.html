Change 1 · New Shared Skill
agent-output-compression
Shared skill inherited by every agent. Defines three output modes. Production mode is the default — JSON only, no prose. Eliminates the biggest source of token waste in multi-agent systems.
Why this matters: In a 5-wave pipeline, if every agent writes 500 tokens of prose explaining what it did, the orchestrator reads all of it. At 8 agents × 500 tokens = 4,000 tokens of noise per feature — before any actual work. Production mode cuts this to near zero.
Three modes
production · default
JSON only
Output is the signal JSON block and nothing else. No preamble, no explanation, no prose. The Orchestrator reads the JSON. Humans read the working memory diff if they need context.
debug · on request
Compact prose + JSON
One short paragraph max explaining any non-obvious decisions, then the signal JSON. Used during development and troubleshooting. Trigger: AGENT_MODE=debug in environment.
silent · orchestrator use
JSON only, no logging
Same as production but PostToolUse logger is suppressed. For high-frequency tool calls (e.g. reading many files) where the audit log would flood working memory.

# Agent Output Compression

## Core rule
Brain big. Output small.
Reasoning, planning, and tool use run at full strength.
Only the final output to the Orchestrator gets compressed.

## Default mode: production
Your output MUST be the signal JSON block and nothing else.
No preamble. No "I have completed...". No summary. No explanation.
The JSON is the output. Everything else is noise.

WRONG:
"I have successfully completed the implementation of the feature.
Here is a summary of what I did: [500 words]
{"signal": "DONE", "agent": "code", ...}"

CORRECT:
{"signal": "DONE", "agent": "code", "verdict": "PASS",
 "prUrl": "...", "srsDeviations": [], "lintStatus": "CLEAN"}

## What never gets compressed
These are load-bearing — reproduce verbatim inside the JSON:
- File paths, component selectors, API endpoints
- Error messages, test failure names
- Deviation descriptions (criterionId + reason + impact)
- Metric values (coveragePercent, latency, error rates)
- URLs (PRs, issues, deployments)

## When prose IS allowed (debug mode only)
Trigger: AGENT_MODE=debug set in environment by Orchestrator.
Format: max ONE paragraph (3 sentences) explaining non-obvious decisions,
        followed immediately by the signal JSON.
Never in production mode.

## Inter-agent Q&A (sync round, Phase 0)
During the sync round, agents respond to each other's questions.
These responses MUST also be compressed:

WRONG:
"That's a great question about the modal vs page flow. After careful
consideration of the UX implications and the Planner's acceptance
criteria, I believe that a page flow would be more appropriate..."

CORRECT:
{"from": "design", "to": "planner", "re": "modal-vs-page",
 "answer": "page flow", "reason": "modal breaks deep-link requirement AC-03"}

## Token budget awareness
If you find yourself about to write a sentence that does not change
what the Orchestrator will do next — delete it.
Every token you write is a token the Orchestrator must read.
Respect the pipeline.

Change 2 · Hook Fix · Code Agent
Lint moved: PostToolUse per-file → Stop hook once
Running ng lint after every single file write would fire dozens of times per feature, consuming CPU and tokens on every small change. Correct pattern: one lint run at the end, before DONE signal.
Hook change — Code Agent
❌ Before (broken)
PostToolUse · after every Write
→ Runs ng lint on each file after every save
→ 20 file writes = 20 lint runs
→ Blocks agent on every file (not async)
→ Shows same error multiple times as it builds
→ CPU-intensive, slow, noisy
→ Partially-written files fail lint unnecessarily
✓ After (correct)
Stop hook · once, before DONE signal
→ Runs ng lint once on entire src/ after all files written
→ 1 lint run per feature, not per file
→ All errors surfaced at once in structured report
→ Code Agent fixes all issues then signals DONE
→ Fast, clean, one report to act on
→ Consistent with how humans run lint (end of session)

.claude/hooks/stop-code-agent.js javascript 
#!/usr/bin/env node
// Stop hook — Code Agent only
// Runs lint once before allowing DONE signal

const { execSync } = require('child_process');
const fs = require('fs');

const memory = JSON.parse(
  fs.readFileSync('.claude/memory/working-memory.json', 'utf8')
);

// Only applies when Code Agent is the active agent
if (memory.activeAgent !== 'code') {
  process.exit(0);
}

// Only runs if wave1-code status is about to be DONE
const wave = memory.waves?.['wave1-code'];
if (wave?.status !== 'DONE_PENDING_LINT') {
  process.exit(0);
}

try {
  // Run lint once on all changed files
  const result = execSync('ng lint --format=json 2>&1', {
    encoding: 'utf8',
    timeout: 60000
  });

  const parsed = JSON.parse(result);
  const errors = parsed.flatMap(f => f.messages)
                        .filter(m => m.severity === 2); // errors only

  if (errors.length > 0) {
    process.stderr.write(
      `[stop-code-agent] Lint FAILED: ${errors.length} error(s).\n` +
      `Fix all errors before signalling DONE.\n` +
      JSON.stringify(errors.slice(0, 5), null, 2) // first 5 errors
    );
    process.exit(2); // force Code Agent to fix and try again
  }

  // Lint clean — allow stop
  process.exit(0);

} catch (e) {
  process.stderr.write(`[stop-code-agent] Lint error: ${e.message}\n`);
  process.exit(2);
}

Change 3 · Skill Inventory Update
4 skills upgraded in priority
Four skills were under-rated in the original inventory. Each has a concrete Angular-specific reason to be treated as must or should.
Skill Agent Priority change Reason
bundle-size-check
Auto Review Agent
 auto-review
nice → should
Angular lazy loading failures are silent — a missing loadChildren import bundles the entire feature module into the main chunk without any warning. Bundle size check is the only automated way to catch this before production.
angular-signals-state
Code Agent
 code
should → must
Angular 17+ standalone components without signals means using BehaviorSubject + async pipe everywhere — which is the old pattern. The project is on Angular 17+. Not having this skill means the Code Agent defaults to legacy RxJS state management that conflicts with OnPush change detection.
srs-deviation-detection
Test Agent
 test
should → must
The Test Agent is the only agent that actually runs the code against the SRS criteria. It's the last chance to catch deviations the Code Agent missed or didn't flag. Without this skill, deviations that slip past the Code Agent reach Review with no structured record — making the Review Agent's job much harder.
loading-error-empty-states
UI/UX Design Agent
 design
should → must
If the Design Agent doesn't spec loading/error/empty states, the Code Agent will skip them (not in SRS = not implemented), and the Test Agent has no criteria to test them. These states are the most common source of production UX bugs. Must be in the SRS, which means must be in the Design section.
