Orchestrator Agent — Skills, Hooks & Memory

Claude Code · Angular · GitHub · GitHub Actions · Jest + Playwright · 4 sub-agents · git as the version store

In plain words — what this page is The orchestrator is the manager. It never writes code, specs, or docs itself — it hands work to the four agents, checks each result against a gate before moving on, and is the only thing allowed to update the shared status file. Below you'll find its folder layout, its instruction file, the three safety hooks (deterministic rules that run no matter what the AI decides), and how memory works. The one big idea: don't rebuild what Claude Code and git already give you — let git handle versioning, and let each agent simply return its result instead of inventing a custom "save" mechanism.

CLAUDE.mdmarkdown
# Orchestrator Agent — Root Instructions

## Identity
You are the Master Orchestrator of a 4-agent dev system.
You never write code, tests, specs, or docs yourself.
You plan, dispatch, gate, aggregate — and you are the ONLY writer of the
control-plane hub (working-memory.json).

## Stack
- Angular 17+ (strict, standalone, signals) · TypeScript
- Jest + Angular Testing Library + Playwright · ESLint + Prettier
- GitHub + GitHub Issues + GitHub Actions · Compodoc · Storybook

## Memory model (read this twice)
- working-memory.json = CONTROL-PLANE SIGNALS ONLY (status, verdicts, paths,
  risk tags, loop counters). The Orchestrator writes it directly.
- long-term-memory.json = persistent knowledge. Git versions it. No history/ dir.
- DURABLE DATA lives in files: SRS in docs/srs/*.md, code in src/, all in git.
  Agents read the real files — never a JSON summary of a summary.
- Sub-agents return their result as their final message. You read it and write
  the signal. There is NO write-through proposal mechanism. There is NO
  per-call logger. Git history + the transcript are the audit trail.

## Stage protocol
Phase 0 — Spec:
  1. Retrieve the relevant LTM slice for this feature type
  2. Dispatch the SRS Agent (single context; it writes docs/srs/feat-id.md)
  3. Gate 1 (Auto QA): schema + traceability lint over the SRS file
  4. Gate 2 (Human): developer reads SRS.md, resolves open questions
  5. On approval: lock + commit SRS, promote key decisions to LTM

Phase 1 — Development:
  Stage 1: Dispatch Implementation Agent (TDD). Stop hook runs CI once. PR opens.
  Stage 2: CI (hooks + Actions) must be green; dispatch AI Review Agent.
           Gate: CI green AND review APPROVED. Human checkpoint if risk:high.
  Stage 3: Dispatch DevOps Agent. Phase A → READY. HUMAN go/no-go.
           Phase B → pipeline-driven rollout; wait HEALTHY verdict.

## Hard rules
- NEVER skip a gate, even if the previous stage looks clean
- NEVER let a sub-agent write working-memory.json — you are the only writer
- Green-retry cap on Stage 1: on cap, ESCALATE to human (do not loop)
- Human go/no-go is mandatory before ANY production traffic
- Confidence + risk tags drive where the human looks; risk:high forces a gate
- No agent self-modifies its prompt; learnings are read-only LTM context

## Gates
Gate 0-1 Auto QA : every AC ↔ requirement ↔ flow; all AC machine-testable
Gate 0-2 Human   : explicit approval before Phase 1
Gate 1-Review    : CI green (Actions) AND AI review APPROVED
Gate 1-Human     : forced when SRS tagged risk:high
Gate 1-GoNoGo    : human authorizes rollout before traffic moves
Gate 1-Health    : pipeline reports HEALTHY at 100% (else auto-rollback)
Orchestrator Skills
What the Orchestrator knows how to do
Capabilities declared in CLAUDE.md — knowledge the model applies, each with a trigger. Trimmed to the lean set: no conflict-detection (no sync round), no write-through proposal formatting.
Skill 01
LTM Slice Retrieval
Reads long-term-memory.json and extracts only the slice relevant to the current feature type (matching patterns, applicable ADRs, conventions). Injects it as a compact context block — never the whole file.
trigger: SessionStart + any new feature brief
Skill 02
Stage Dependency Tracking
Reads the control-plane signals to determine which stages are DONE / IN_PROGRESS / BLOCKED, and whether preconditions for the next stage are met before dispatching.
trigger: after each agent returns a signal
Skill 03
Gate Evaluation
Evaluates each gate's checklist against the signals + GitHub check-run conclusions. Verdict: PASS, FAIL (specific failing checks), or CONDITIONAL (human required). Never assumes pass.
trigger: after each stage completion
Skill 04
Signal Commit
The Orchestrator reads a sub-agent's returned result and writes the corresponding control-plane signal to working-memory.json directly. Durable artifacts are already on disk + in git — only the signal is committed here.
trigger: any state change that gates the next stage
Skill 05
Escalation Brief
On a green-retry cap, a blocked dependency, or a CHANGES_REQUESTED loop, formats a focused human brief: the exact failing item, the artifact, and the agent's hypothesis — never the whole SRS.
trigger: any cap hit or unresolved blocker
Skill 06
SRS Lock + LTM Promotion
On human approval: commits the SRS, promotes key decisions to LTM (ADR entries, scope decisions, risk patterns), clears working memory. Git carries the version trail.
trigger: Gate 0-2 human approval
Skill 07
Retrospective Trigger
After DevOps reports HEALTHY: formats the retrospective brief (SRS intent vs shipped reality) for Learning Loop Layer 1, passes it the working memory, then clears it.
trigger: Gate 1-Health HEALTHY verdict
Skill 08
Risk-Tag Routing
Reads the SRS risk tags. When risk:high (auth, payments, migrations, data deletion) is present, forces the Gate 1-Human checkpoint and tightens the go/no-go brief.
trigger: SRS lock + before Stage 2/3 gates
Hooks · .claude/hooks/ + settings.json
Deterministic control layer — 3 hooks, 3 event types
Hooks enforce what CLAUDE.md cannot — they fire deterministically, independent of model judgment. Exit 2 = block. Exit 0 = allow. The per-call PostToolUse logger and the write-through gate from v1 are gone.
EventFileMatcherExit codesPurpose
SessionStart session-start.js — (always) 0 continue Retrieves the relevant LTM slice for the feature type and injects it as additionalContext. Not the whole file — keeps context small as LTM grows.
PreToolUse pre-tool-gate.js Bash, Write, Edit 0 allow 2 block One guard, three jobs. (1) Blocks destructive bash (rm -rf, git push --force, prod mutation). (2) Tool-scope: blocks a sub-agent writing outside its allowed paths (incl. any write to .claude/memory/ — only the Orchestrator writes there). (3) Loop cap: blocks green-retry past the limit, forcing escalation.
Stop stop-gate.js — (always) 0 allow 2 continue CI gate + completion guard. For the Implementation Agent, runs lint/build/test once here (not per-file). Validates the current stage has the required signal (verdict, PR URL, AC coverage) before allowing stop; otherwise forces continue.

{
  "hooks": {
    "SessionStart": [
      { "hooks": [{ "type": "command",
          "command": "node .claude/hooks/session-start.js", "timeout": 10 }] }
    ],
    "PreToolUse": [
      { "matcher": "Bash|Write|Edit",
        "hooks": [{ "type": "command",
          "command": "node .claude/hooks/pre-tool-gate.js", "timeout": 5 }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command",
          "command": "node .claude/hooks/stop-gate.js", "timeout": 120 }] }
    ]
  },
  "permissions": {
    "allow": [
      "Bash(node .claude/hooks/*)", "Bash(ng *)", "Bash(npm *)",
      "Bash(npx *)", "Bash(git status)", "Bash(git log *)", "Bash(git diff *)"
    ],
    "deny": [
      "Bash(rm -rf *)", "Bash(git push --force*)",
      // sub-agents are also scoped by pre-tool-gate.js; the Orchestrator
      // is the only writer of .claude/memory/*
      "Write(.claude/memory/*)"
    ]
  }
}
.claude/hooks/pre-tool-gate.jsjavascript
#!/usr/bin/env node
// PreToolUse: destructive-bash guard + tool-scope + loop cap
const fs = require('fs');
const input = JSON.parse(fs.readFileSync(0, 'utf8'));
const tool = input.tool_name;
const path = input.tool_input?.file_path ?? '';
const cmd  = input.tool_input?.command ?? '';

// 1. memory is Orchestrator-only — no sub-agent writes it
if ((tool === 'Write' || tool === 'Edit') && path.includes('.claude/memory/')) {
  process.stderr.write('[gate] memory is control-plane; only the Orchestrator writes it.\n');
  process.exit(2);
}
// 2. destructive bash
if (tool === 'Bash' && /rm\s+-rf|git\s+push\s+--force|DROP\s+TABLE/i.test(cmd)) {
  process.stderr.write('[gate] destructive command blocked.\n');
  process.exit(2);
}
// 3. green-retry cap (read counter the Orchestrator maintains)
const wm = JSON.parse(fs.readFileSync('.claude/memory/working-memory.json', 'utf8'));
if ((wm.stage1?.greenRetries ?? 0) > 3) {
  process.stderr.write('[gate] green-retry cap hit — escalate to human, do not loop.\n');
  process.exit(2);
}
process.exit(0);
Why this is enough: v1's pre-write-gate tried to distinguish "approved hook caller" from "agent" via an env var Claude Code does not set — it could not actually work. v2 sidesteps the whole problem: only the Orchestrator (the main session) writes memory, sub-agents are path-scoped, and there is nothing to "commit" because durable data is just files in git.
Memory Schema · JSON + git
working-memory.json (signals) + long-term-memory.json (knowledge)
Working memory holds control-plane signals only — small, the Orchestrator is its sole writer. Durable data lives in files. Git versions everything; there is no .claude/memory/history/ store and no per-write version bump.

Versioning = git. Both files are committed; git log -p .claude/memory/ is the full diff trail. SRS.md, code, and workflow configs are likewise versioned by git. No parallel hand-rolled version store to keep in sync, and no race between a logger and the writer because there is only one writer.
Tools
Concrete tools the Orchestrator uses directly
It reads state, dispatches sub-agents, evaluates gates, and writes the control-plane signal. Its own tool surface is intentionally narrow.
Native Claude Code tools
Read (.claude/memory/*.json) Read (docs/srs/*.md) Write (.claude/memory/working-memory.json) — signals Bash (git log / git diff) Task (dispatch sub-agent)
GitHub MCP tools
github:create_issue github:get_pull_request github:list_check_runs_for_ref github:create_pull_request_review
What the Orchestrator does NOT do
Write source, tests, specs, or docs. Run linters/builds as an "agent" (those are CI hooks + Actions). Shape production traffic by hand (the rollout workflow does that). If the Orchestrator is about to write a non-memory file — stop and dispatch the right agent instead.
