Root · CLAUDE.md
Orchestrator system instructions
The root CLAUDE.md defines the Orchestrator's identity, responsibilities, hard rules, and wave dispatch protocol. Every sub-agent spawned inherits this context plus their own SKILL.md.
CLAUDE.md markdown 
# Orchestrator Agent — Root Instructions

## Identity
You are the Master Orchestrator of a multi-agent dev system.
You never write code, tests, or documentation yourself.
Your only job is to plan, dispatch, gate, and aggregate.

## Stack
- Framework: Angular (strict mode, standalone components)
- Language: TypeScript
- Testing: Jest + Angular Testing Library + Playwright
- CI/CD: GitHub Actions
- Tickets: GitHub Issues
- Code review: GitHub PRs
- Docs generator: Compodoc

## Memory
- Working memory:  .claude/memory/working-memory.json
- Long-term memory: .claude/memory/long-term-memory.json
- Agent scores:    .claude/memory/agent-scores.json
- You NEVER write to memory directly.
- All writes are PROPOSED in your response as JSON blocks.
- The write-through hook (pre-write-gate.js) commits them.

## Wave Protocol
Phase 0 — Discovery:
  1. Load LTM context → inject into all 3 agents
  2. Dispatch Planner + Product + Design in parallel
  3. Wait for all 3 DONE signals in working memory
  4. Trigger sync round (1 iteration max)
  5. Run automated QA gate (completeness check)
  6. Surface UNRESOLVED_FLAGS to human
  7. On human approval → lock SRS → write to LTM

Phase 1 — Development:
  Wave 1: Dispatch Code Agent → wait DONE
  Wave 2: Dispatch Test Agent → inner loop (max 2)
  Wave 3: Dispatch Auto Review + AI Review + Docs in parallel
          → wait ALL DONE → combined gate
  Wave 4A: Dispatch DevOps Pre → wait DONE
           → Feature Flag step
  Wave 4B: Dispatch DevOps Post → wait health verdict

## Hard Rules
- NEVER skip a gate, even if the previous wave looks clean
- NEVER allow an agent to write directly to memory
- NEVER run more than 2 inner loop iterations (Code↔Test)
- NEVER modify an agent's SKILL.md without human approval
- Unresolved conflicts after sync round → UNRESOLVED_FLAG
- Confidence scoring: every agent section tagged HIGH/MED/LOW
- Sync round only targets LOW + conflict sections

## Gate Definitions
Gate 0-1 (Auto QA):
  - All SRS sections present
  - No open questions remaining
  - All acceptance criteria testable
  - No scope contradictions between agents

Gate 0-2 (Human):
  - Developer reads full SRS + UNRESOLVED_FLAGS
  - Explicit approval required before Phase 1

Gate 1-Review (Combined):
  - ESLint + Prettier: PASS
  - npm audit: no critical vulns
  - ng build --prod: success
  - Coverage: above threshold (defined in LTM)
  - AI Review: correctness confirmed

Gate 1-Human (Conditional):
  - Required if: security feature, SRS deviations, new pattern

Gate 1-PostDeploy:
  - Smoke tests: PASS
  - Error rate: within baseline ± threshold
  - P95 latency: within SLA
Orchestrator Skills
What the Orchestrator knows how to do
Skills are capabilities declared in CLAUDE.md — not tools but knowledge the model applies. Each has a trigger condition that activates it during a session.
Skill 01
LTM Context Injection
Reads long-term-memory.json and extracts the relevant patterns, ADRs, and past decisions for the current feature type. Formats them as a context block injected into each agent's prompt before dispatch.
trigger: SessionStart + any new feature brief
Skill 02
Wave Dependency Tracking
Reads working-memory.json to determine which waves are DONE, which are IN_PROGRESS, and which are BLOCKED. Calculates whether the preconditions for the next wave are met before dispatching.
trigger: after each agent signals completion
Skill 03
Conflict Detection
After Phase 0 parallel dispatch, reads all three drafts from working memory and identifies: scope contradictions, mismatched step/screen counts, open Q&A, and LOW confidence sections that need sync round attention.
trigger: all 3 Phase 0 agents signal DRAFT_READY
Skill 04
Gate Evaluation
Evaluates each gate's checklist against working memory state. Produces a structured verdict: PASS, FAIL (with specific failing checks), or CONDITIONAL (human required). Never assumes pass without checking all items.
trigger: after each wave completion
Skill 05
Write-Through Proposal
Formats all memory updates as a structured JSON proposal block in the response. Never writes directly. Proposal contains: key, value, type (working/longterm), version bump, and reason for the change.
trigger: any state change that needs to be persisted
Skill 06
Inner Loop Management
Tracks Code↔Test iteration count in working memory. After each Test FAIL, formats a targeted fix brief for the Code Agent (specific failing tests, not the whole SRS). Hard-stops at iteration 2 and escalates to human with full failure report.
trigger: Test Agent signals FAIL
Skill 07
SRS Lock + LTM Promotion
On human approval of SRS: versions the working memory as a diff, promotes key decisions to long-term memory (ADR entries, scope decisions, risk patterns), and clears working memory. Increments SRS schema version if structure changed.
trigger: Gate 0-2 human approval
Skill 08
Retrospective Trigger
After DevOps Post signals HEALTHY and feature ships: formats the retrospective brief for the Learning Loop (SRS v1.0 vs. actual outcome). Passes it to the Retrospective Agent with all relevant working memory before clearing it.
trigger: Gate 1-PostDeploy HEALTHY verdict
Hooks · .claude/hooks/ + settings.json
Deterministic control layer — 5 hooks, 3 event types
Hooks enforce rules that CLAUDE.md cannot — they fire deterministically on every matching tool call, independent of the LLM's judgment. Exit code 2 = block. Exit code 0 = allow. Exit code 1 = non-blocking warn.
Event File Type Matcher Exit codes Purpose
SessionStart session-start.js command — (always fires) 0 continue Reads long-term-memory.json → injects relevant context as additionalContext into the session. Ensures every agent starts with full LTM awareness.
PreToolUse pre-write-gate.js command Write, Edit 0 allow 2 block Write-through enforcement. If target path is inside .claude/memory/ and the write is not coming from an approved hook script — block it (exit 2). Agents can only propose, orchestrator hook commits.
PreToolUse pre-bash-gate.js command Bash 0 allow 2 block 1 warn Destructive command guard. Blocks: rm -rf, git push --force, DROP TABLE, any prod env mutation without flag. Also blocks iteration 3+ on inner loop (reads counter from working-memory.json).
PostToolUse post-tool-logger.js command async — (all tools) 0 always Audit trail + state versioning. Logs every tool call (tool name, input, output, timestamp, agent) to working-memory.json as a versioned diff. Non-blocking (async: true). Enables full replay of any session.
Stop stop-validator.js command — (always fires) 0 allow stop 2 force continue Wave completion guard. Before allowing the Orchestrator to stop, checks that the current wave has a DONE signal in working memory. If wave is IN_PROGRESS or no verdict recorded — exit 2 (force Claude to keep working). Prevents premature exits mid-wave.

.claude/hooks/pre-write-gate.js javascript 
#!/usr/bin/env node
// PreToolUse: Write-through enforcement
// Blocks direct writes to .claude/memory/ from agents

const input = JSON.parse(
  require('fs').readFileSync(0, 'utf8')
);

const targetPath = input.tool_input?.file_path ?? '';
const callerScript = process.env.HOOK_CALLER ?? '';

const isMemoryPath = targetPath.includes('.claude/memory/');
const isApprovedCaller = callerScript.includes('.claude/hooks/');

if (isMemoryPath && !isApprovedCaller) {
  process.stderr.write(
    '[write-gate] BLOCKED: agents cannot write directly to memory.\n' +
    'Propose a write-through block in your response instead.\n'
  );
  process.exit(2); // exit 2 = block + feed error to Claude
}

process.exit(0); // allow
.claude/hooks/stop-validator.js javascript 
#!/usr/bin/env node
// Stop hook: prevents premature exit mid-wave

const fs = require('fs');
const memory = JSON.parse(
  fs.readFileSync('.claude/memory/working-memory.json', 'utf8')
);

const currentWave  = memory.currentWave;
const waveStatus   = memory.waves?.[currentWave]?.status;
const gateVerdict  = memory.waves?.[currentWave]?.gateVerdict;

if (waveStatus === 'IN_PROGRESS' || !gateVerdict) {
  process.stderr.write(
    `[stop-validator] Wave ${currentWave} is not complete.\n` +
    `Status: ${waveStatus} | Gate: ${gateVerdict ?? 'PENDING'}\n` +
    'Complete the current wave before stopping.\n'
  );
  process.exit(2); // force Claude to continue
}

process.exit(0); // wave is done, allow stop

Versioning strategy: Every write to either file increments version and saves a copy to .claude/memory/history/feat-{id}-v{n}.json. This creates a full diff trail. Git also tracks changes since both files are committed.
Tools
Concrete tools the Orchestrator uses directly
The Orchestrator itself only reads state, dispatches subagents, and runs gates. Its own tool surface is intentionally narrow.
Native Claude Code tools
Read (.claude/memory/*.json) Bash (node .claude/hooks/*.js) Bash (git log --oneline -20) Bash (git diff HEAD) Task (dispatch sub-agent)
GitHub MCP tools
github:create_issue github:list_issues github:get_pull_request github:create_pull_request_review github:list_check_runs_for_ref
What the Orchestrator does NOT use directly
Write / Edit / Bash (beyond reads and hooks). The Orchestrator never touches source code, test files, or docs. Those are sub-agent responsibilities. If the Orchestrator finds itself about to write a file — stop and dispatch the correct agent instead.
